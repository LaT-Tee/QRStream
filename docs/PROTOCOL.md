# QX4 帧协议规范

本文档描述 QRStream 的空中帧格式与编解码算法，足以让第三方独立实现兼容的发送端或接收端。参考实现：[`src/codec.js`](../src/codec.js)、[`src/sender-core.js`](../src/sender-core.js)。

## 1. 总览

```
文件/文本 ──► [可选 deflate] ──────────► 数据包 ──► 切成 K 个 C 字节源块
                                                          │
                       系统帧 SEQ=0..K-1（源块原样） ◄──────┤
                       冗余帧 SEQ≥K（若干源块的 XOR）◄──────┘   ← GF(2) 随机线性喷泉码
                                    │
                         Base45 → QR（Alphanumeric 模式）→ 屏幕 ──► 摄像头
```

接收端收到**任意** K + ε 个线性无关的帧即可还原（ε 平均约 1.6），漏掉的帧不需要等下一轮重播。

## 2. 数据包（Packet）

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 4 | `metaLen`，大端 uint32 |
| 4 | metaLen | meta，UTF-8 JSON |
| 4 + metaLen | 其余 | 数据（可能已 deflate） |

meta 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `t` | `"text"` \| `"file"` | 类型 |
| `name` | string | 文件名（文本为 `text.txt`） |
| `mime` | string | MIME 类型 |
| `z` | bool | 数据是否经过 zlib 格式 deflate（`CompressionStream('deflate')`） |
| `len` | number | **解压后**数据的字节数，用于校验 |

数据包总长记为 `LEN`。选取块大小 `C`（4 的倍数，≥ 52），`K = ceil(LEN / C)`，末块补 0 到 `K × C`。

`CRC` = CRC-32/ISO-HDLC（与 zlib 相同）作用于数据包前 `LEN` 字节，8 位大写十六进制。

## 3. 帧文本

```
QX4:<SID>:<K>:<LEN>:<CRC>:<SEQ>:<FCK>:<PAYLOAD>*
```

| 字段 | 格式 | 说明 |
|---|---|---|
| `SID` | 4 位 `[0-9A-Z]` | 会话 ID，每次生成随机 |
| `K` | 十进制 | 源块数，1 ≤ K ≤ 20000 |
| `LEN` | 十进制 | 数据包长度；必须满足 `ceil(LEN / C) == K` |
| `CRC` | 8 位大写 hex | 整包 CRC32 |
| `SEQ` | 十进制 | 帧序号，见第 4 节 |
| `FCK` | 8 位大写 hex | **本帧载荷**（解码后的 C 字节）的 CRC32 |
| `PAYLOAD` | Base45（RFC 9285） | C 字节载荷，长度 = 1.5 × C 字符 |
| `*` | 字面量 | 结束符。Base45 字母表含空格，结束符防止扫码库裁掉末尾空格 |

所有字符都属于 QR Alphanumeric 字符集（`0-9 A-Z 空格 $ % * + - . / :`），因此整帧以 Alphanumeric 模式编码，每字节约 8.25 bit，比 Base64 + Byte 模式（约 10.7 bit）省约 23%。

解析时按前 7 个 `:` 切分（Base45 本身含 `:`），再去掉末尾 `*`。

**兼容性**：接收端同时接受 `QX3:` 前缀，此时 `FCK` 为 4 位 hex（CRC32 的低 16 位），其余相同。

## 4. 喷泉码

### 4.1 系统帧

`SEQ < K`：载荷就是第 `SEQ` 个源块。

### 4.2 冗余帧

`SEQ ≥ K`：载荷 = `rowBits(SID, SEQ, K)` 选中的所有源块按字节 XOR。每个源块被选中的概率为 1/2（稠密随机 GF(2) 编码）。

`rowBits` 必须与参考实现逐位一致：

```js
function rowBits(sid, seq, K) {
  // 1) FNV-1a 32 位哈希 "SID:SEQ" 作为种子
  let h = 2166136261;
  const s = sid + ':' + seq;
  for (let i = 0; i < s.length; i++) { h ^= s.charCodeAt(i); h = Math.imul(h, 16777619); }
  // 2) mulberry32 生成 ceil(K/32) 个 32 位字，第 c 位（字 c>>5 的第 c&31 位）= 是否选中源块 c
  let a = h | 0;
  const W = (K + 31) >>> 5, bits = new Uint32Array(W);
  for (let w = 0; w < W; w++) {
    a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    bits[w] = (t ^ (t >>> 14)) >>> 0;
  }
  // 3) 清掉 ≥K 的位；若全 0，强制选中 seq % K
  if (K & 31) bits[W - 1] &= (1 << (K & 31)) - 1;
  if (bits.every(x => x === 0)) { const c = seq % K; bits[c >>> 5] |= 1 << (c & 31); }
  return bits;
}
```

### 4.3 发送顺序

先按 `SEQ = 0, 1, …, K-1` 播放一轮系统帧，之后 `SEQ = K, K+1, …` 无限播放冗余帧。用户可指定"只播帧"列表（仅系统帧编号）做定向补发。

### 4.4 解码（参考实现）

增量 GF(2) 高斯消元，行阶梯形：

1. 每收到一帧：先用位掩码一次性剥离所有已知源块（只 XOR 载荷），再从最低位起用已有主元行约简；
2. 剩余非零 → 以最低位为主元加入；只剩一位 → 该源块直接已知；全零 → 线性相关，丢弃；
3. 秩达到 K → 从高列到低列回代，得到全部源块；
4. 拼包，校验整包 CRC，解析 meta，按需解压，校验 `len`。

复杂度：每帧 O(r · (K/32 + C/4))，r 为当前秩；回代 O(K² · C / 8) 最坏。参考实现把消元和回代都放在 Web Worker 中。

## 5. RGB 三通道模式

- 一张图的 R、G、B 三个通道各承载一个独立的 QR 帧，依次放置连续 3 个 SEQ；
- 每个通道：深色模块 = 0，浅色模块 = 255。8 种组合色（黑、红、绿、蓝、青、品红、黄、白）；
- 同一会话的 QR **版本固定**（按 `SEQ = 9999999` 的最长帧计算），保证三层模块网格完全对齐；
- 接收端分别取出每个通道作为灰度图识别；失败时再用 `1.6·c − 0.3·(o₁ + o₂)` 做简单的串色补偿后重试。

## 6. 静区与渲染

- 静区 4 模块；
- 渲染时 1 模块 = 1 像素绘制，再按**整数倍**最近邻放大，保证边缘锐利；
- 帧切换跟随 `requestAnimationFrame`，掉帧时不追赶。
